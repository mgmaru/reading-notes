# 『おうちで学べるセキュリティの基本』2026-10-3 疑問3：現在、多いセキュリティホールは何か

## 疑問

> 昨今のセキュリティホールで最も多い原因は何か？ ライブラリの脆弱性が多く、SQLインジェクションなどの基本的な問題は減っているのではないか？

## 回答

**あらゆるシステムについて「原因の第1位はライブラリ」と断定できる統計はありません。** 何を対象にし、何を1件と数えるかで結果が変わります。ただし、Webアプリを考えるなら、ライブラリだけに注目するのは危険です。OWASP Top 10:2025では、**アクセス制御の不備が最も重大なリスクの1位**、設定ミスが2位、ライブラリを含む**ソフトウェア供給網の問題**が3位、インジェクションが5位です。これはリスクの順位であり、全世界のセキュリティホールの発生件数順ではありません（[OWASP Top 10:2025と選定方法](https://top10.owasp.org/2025/0x00_2025-Introduction/)）。

### まず、比較する言葉の軸をそろえる

```text
「どこに問題があるか」            「どんな弱点・失敗か」
自分たちのコード ───────────→  認可チェックの欠落、SQL文の不適切な組み立て
外部ライブラリ ─────────────→  入力処理の欠陥、脆弱な古い版の利用
設定・ビルド・配布の仕組み ──→  意図しない公開、不正な更新の取り込み
```

**「ライブラリの脆弱性」は問題がある場所・部品の話、「SQLインジェクション」は弱点の種類の話**です。したがって二択ではありません。自分たちのコードにも外部ライブラリにも、SQLインジェクションのような弱点が起こり得ます。一方、ライブラリが安全でも、自分のアプリが「他人の注文番号を指定したら注文内容を見られる」ならアクセス制御に問題があります。OWASPも、供給網の問題には第三者コードだけでなくビルド・配布過程の侵害を含め、アクセス制御の不備には他人のレコードへのアクセスを含めています（[OWASP：供給網](https://top10.owasp.org/2025/A03_2025-Software_Supply_Chain_Failures/)、[OWASP：アクセス制御](https://top10.owasp.org/2025/A01_2025-Broken_Access_Control/)）。

### 公開資料から分かる範囲

| 資料・対象 | 分かること | 読み取りの限界 |
| --- | --- | --- |
| **OWASP Top 10:2025**：主にWebアプリのリスク | アクセス制御の不備が1位。設定ミス2位、供給網の問題3位、インジェクション5位 | 調査で見つけた弱点、影響、専門家の評価などを使った**リスク順位**。すべてのアプリ・侵害事件の件数順位ではない |
| **MITRE CWE Top 25:2025**：公開された脆弱性のCVE記録 | XSSが1位、**SQLインジェクションが2位**、認可チェックの欠落が4位 | 約39,000件の公開CVEを基に**頻度と深刻さを組み合わせた順位**。非公開の社内アプリの弱点や、実際の侵害件数は表さない |

根拠：[OWASPの順位と調査方法](https://top10.owasp.org/2025/0x00_2025-Introduction/)、[MITREの順位](https://cwe.mitre.org/top25/archive/2025/2025_cwe_top25.html)と[集計方法](https://cwe.mitre.org/top25/archive/2025/2025_methodology.html)。両資料は**対象も採点方法も違う**ので、順位を直接比較して「SQLインジェクションの方がライブラリの脆弱性より何倍多い」とは言えません。また、OWASPの「供給網の問題」には、脆弱なライブラリの利用以外も含まれます。

**「基本的な対策は普及したから、SQLインジェクションはもう考えなくてよい」とは言えません。** 文字列をつないでSQLを作るコードでは、今も発生し得ます。対策の中心は、ユーザー入力をSQL文の一部として連結せず、**パラメータ化クエリ**でデータとして渡すことです。フレームワークやORMを使っていても、手書きの動的SQLには注意します（[OWASP：SQLインジェクション防止](https://cheatsheetseries.owasp.org/cheatsheets/SQL_Injection_Prevention_Cheat_Sheet.html)）。

### 開発時に確認する順番

1. **自分たちのアプリ**：利用者や権限を変えて、他人のデータ・管理操作にアクセスできないか確かめる。サーバー側で権限を判定する（[OWASP：アクセス制御](https://top10.owasp.org/2025/A01_2025-Broken_Access_Control/)）。
2. **入力を扱うコード**：SQLを文字列連結していないか確認し、パラメータ化クエリを使う（[OWASP：SQLインジェクション防止](https://cheatsheetseries.owasp.org/cheatsheets/SQL_Injection_Prevention_Cheat_Sheet.html)）。
3. **設定と外部部品**：不要な公開や過大な権限を点検し、利用中のライブラリを継続的に調べる（[OWASP：設定ミス](https://top10.owasp.org/2025/A02_2025-Security_Misconfiguration/)、[OWASP：供給網](https://top10.owasp.org/2025/A03_2025-Software_Supply_Chain_Failures/)）。

ライブラリの調査手順は、技術を分けて[疑問3：ライブラリの脆弱性を見つける方法](./basic_security_at_home_20261003_question3_dependency_vulnerability_management.md)にまとめます。
